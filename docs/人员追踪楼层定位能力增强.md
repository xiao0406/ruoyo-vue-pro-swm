# 人员追踪楼层定位能力增强

## 概述

本次开发在现有人员追踪定位体系基础上，新增了 **楼层定位（floorId）** 的全链路支持。当定位数据中 `type='floor'` 时，取 `map_id` 作为人员当前所在楼层的 `floorId`，贯穿三条数据链路透传给前端。所有修改保持向后兼容，不破坏原有业务逻辑。

---

## 二、API 入口一：获取人员实时位置 `getPersonPositionsNew`

### 2.1 入口方法

```
POST ${adminPath}/personTrack/getPersonPositionsNew
```

入口方法位于 `PersonTrackController.getPersonPositionsNew`（第 327 行），接收 `PersonPositions` 请求体（包含 searchName、organizationKey、personTypeList），调用 `PersonTrackService.queryPersonsFromDatabase` 获取人员实时位置列表。

### 2.2 调用链路

```
Controller.getPersonPositionsNew
  └── PersonTrackService.queryPersonsFromDatabase
        └── ExternalCoordinateDataServiceImpl.getLatestLocationsByIdCards  [改动点 ①]
        └── PersonTrackService.getBatteryLevelsByIdCards
        └── PersonTrackService.getWorkHoursFromAttendanceBatch
        └── PersonTrackService.getAttendanceStatusFromAttendanceBatch
        └── PersonTrackService.createPersonPositionWithColors            [改动点 ②]
```

### 2.3 改动点详解

#### 改动点 ①：`ExternalCoordinateDataServiceImpl.getLatestLocationsByIdCards`

**文件**：`service/impl/ExternalCoordinateDataServiceImpl.java`

**改动说明**：在查询 `external_coordinate_data` 表的 TDengine SQL 中，增加 `type` 和 `map_id` 两个字段的 `LAST_ROW` 取值，并在组装 `locationInfo` Map 时一并放入。

**改动前 SQL**：

```sql
SELECT LAST_ROW(id_card), LAST_ROW(x), LAST_ROW(y), LAST_ROW(time)
  FROM {dbname}.external_coordinate_data
  WHERE ... PARTITION BY id_card
```

**改动后 SQL**：

```sql
SELECT LAST_ROW(id_card), LAST_ROW(x), LAST_ROW(y), LAST_ROW(time),
       LAST_ROW(type), LAST_ROW(map_id)
  FROM {dbname}.external_coordinate_data
  WHERE ... PARTITION BY id_card
```

**数据组装**：原 `locationInfo` Map 新增两个 key：

```java
locationInfo.put("type", typeObj);
locationInfo.put("map_id", mapIdObj);
```

返回给调用方的 `Map<String, Map<String, Object>>` 中，每个身份证对应的 `locationInfo` 均携带了 `type` 和 `map_id`。

---

#### 改动点 ②：`PersonTrackService.queryPersonsFromDatabase` 解析 floorId

**文件**：`service/PersonTrackService.java`

**改动说明**：从 `externalCoordinateDataService` 返回的 `locationInfo` 中解析 `type` 和 `map_id`，计算 `floorId`，并将 `floorId` 写入人员位置对象，传递给 `createPersonPositionWithColors`。

**核心逻辑**：

```java
// 从 locationInfo 中取值（兼容 TDengine 返回的字符串 "null"）
Object typeObj = locationInfo.get("type");
Object mapIdObj = locationInfo.get("map_id");

String type = (typeObj != null && !"null".equals(typeObj.toString()))
              ? typeObj.toString() : null;
String mapId = (mapIdObj != null && !"null".equals(mapIdObj.toString()))
               ? mapIdObj.toString() : null;

// 当 type='floor' 时，取 mapId 作为 floorId
String floorId = ("floor".equals(type)) ? mapId : null;

// 将 floorId 传入位置构建方法
Map<String, Object> position = createPersonPositionWithColors(
    ..., safetyStrList, batteryMap, floorId);
```

**null 安全处理**：
- `floorId` 为 `null` 时，写入 `""`（空字符串）而非 `null`，避免前端 JSON 解析异常
- `createPersonPositionWithColors` 方法签名新增 `String floorId` 参数

## 四、API 入口三：获取区域围栏时间线 `getAreaFenceDataByIdCardByDateTime`

### 4.1 入口方法

```
GET ${adminPath}/personTrack/getAreaFenceDataByIdCardByDateTime?idCard=xxx&startDate=xxx&endDate=xxx
```

入口方法位于 `PersonTrackController.getAreaFenceDataByIdCardByDateTime`（第 1191 行），在原有 `area_fence_data` 区域围栏数据基础上，新增 `external_coordinate_data` 的楼层切换记录，合并后统一按时间升序返回。

### 4.2 调用链路

```
Controller.getAreaFenceDataByIdCardByDateTime   [改动点 ④]
  ├── HelmetCacheService.getAssignedDeviceFromCache         // 根据身份证查设备ID
  ├── Controller.queryAreaFenceDataByDeviceId              // 原有：查 area_fence_data
  ├── Controller.queryFloorDataByIdCard                     // 新增：查楼层切换记录
  ├── SwmSiteMapManagementService.findByIds                 // 新增：mapId→mapName 映射
  └── 合并 + 排序 → 返回
```

### 4.3 改动点详解

#### 改动点 ④：`getAreaFenceDataByIdCardByDateTime` — 5 步处理流程

**文件**：`web/PersonTrackController.java`

**第 1 步**：根据身份证从 Redis 缓存获取设备ID（原有逻辑）

```java
String deviceId = helmetCacheService.getAssignedDeviceFromCache(idCard, swmHelmetDeviceService);
```

**第 2 步**：查询 `area_fence_data` 表，获取区域围栏记录（原有逻辑）

```java
List<Map<String, Object>> areaFenceData = queryAreaFenceDataByDeviceId(deviceId, ...);
```

**第 3 步**（新增）：查询 `external_coordinate_data` 表，按 `type='floor'` 和 `map_id` 分组，取每个分组的最早时间

```java
List<Map<String, Object>> floorData = queryFloorDataByIdCard(idCard, ...);
```

调用新增的 `queryFloorDataByIdCard` 私有方法，SQL 如下：

```sql
SELECT FIRST(time), FIRST(map_id)
  FROM {dbname}.external_coordinate_data
  WHERE id_card = '{idCard}'
    AND type = 'floor'
    AND time >= '{startDate}' AND time <= '{endDate}'
  GROUP BY map_id
  ORDER BY FIRST(time) ASC
```

返回每条记录含 `{time, map_id}`。

**第 4 步**（新增）：根据 `map_id` 批量查询底图管理表，映射为 `mapId → mapName`

```java
Map<String, String> mapIdToName = buildMapIdToNameMap(mapIds);
```

调用新增的 `buildMapIdToNameMap` 私有方法，内部调用 `SwmSiteMapManagementService.findByIds(validIds)`，该方法委托 DAO 执行批量查询（见第 5 节）。

**第 5 步**（新增）：合并两条数据源，统一按时间升序排序

```java
List<Map<String, Object>> mergedData = new ArrayList<>(areaFenceData);
for (Map<String, Object> item : floorData) {
    Map<String, Object> newItem = new HashMap<>();
    String mapId = String.valueOf(item.get("map_id"));
    String time = String.valueOf(item.get("time"));
    newItem.put("time", convertUtcToBeijingTime(time));
    newItem.put("area_name",
        mapIdToName.containsKey(mapId) ? mapIdToName.get(mapId) : mapId);
    mergedData.add(newItem);
}
mergedData.sort((a, b) ->
    String.valueOf(a.get("time")).compareTo(String.valueOf(b.get("time"))));
```

**新增私有方法**：

| 方法名 | 所在文件 | 职责 |
|--------|----------|------|
| `queryFloorDataByIdCard` | PersonTrackController | 从 TDengine 查询 `type='floor'` 楼层切换记录 |
| `buildMapIdToNameMap` | PersonTrackController | 批量查底图管理表，建立 mapId→mapName 映射 |

## 五、支撑层改动（Service → DAO → XML）

以上三个 API 入口均依赖以下支撑层新增的方法。

### 5.1 SwmSiteMapManagementService.findByIds

**文件**：`service/SwmSiteMapManagementService.java`

新增方法，供 Controller 的 `buildMapIdToNameMap` 调用：

```java
public List<SwmSiteMapManagement> findByIds(List<String> ids) {
    if (ids == null || ids.isEmpty()) {
        return new ArrayList<>();
    }
    return dao.findByIds(ids);
}
```

### 5.2 SwmSiteMapManagementDao.findByIds

**文件**：`dao/SwmSiteMapManagementDao.java`

新增 DAO 方法声明：

```java
List<SwmSiteMapManagement> findByIds(@Param("ids") List<String> ids);
```

### 5.3 SwmSiteMapManagementDao.xml — findByIds

**文件**：`resources/mappings/modules/swm/SwmSiteMapManagementDao.xml`

新增 SQL 映射：

```xml
<select id="findByIds" resultType="SwmSiteMapManagement">
    SELECT a.`id` AS "id", a.`map_name` AS "mapName"
    FROM `swm_site_map_management` a
    WHERE a.`id` IN
    <foreach collection="ids" item="id" open="(" separator="," close=")">
        #{id}
    </foreach>
</select>
```

**设计说明**：
- **不走 status 条件过滤**，即使底图被软删除也能查到，确保轨迹历史数据中楼层名称的完整性
- 仅返回 `id` 和 `mapName` 两个字段，最小化数据暴露
- 使用 `IN` 子句批量查询，避免循环单条查询带来的性能损耗

## 六、数据规范

本次改动依赖 `external_coordinate_data` 表中每条定位数据均携带以下两个字段：

| 字段名 | 类型 | 含义 | 示例 |
|--------|------|------|------|
| `type` | string | 定位类型，`'floor'` 表示楼层定位 | `floor` |
| `map_id` | string | 底图/楼层 ID（对应 `swm_site_map_management.id`） | `1f2a3b4c5d6e...` |

当 `type = 'floor'` 时，`map_id` 的值即为人员所在楼层的 `floorId`。

## 七、前端影响与兼容性

| 影响点 | 说明 |
|--------|------|
| `floorId` 字段 | 人员实时位置、轨迹点均新增 `floorId` 字段，前端可根据此字段在对应楼层底图上渲染人员 |
| 时间线事件数据量增加 | `getAreaFenceDataByIdCardByDateTime` 返回的时间线数据可能增加（新增楼层切换记录） |
| 向后兼容 | 未带 `type`/`map_id` 的历史数据，`floorId` 为空字符串，不影响原有渲染逻辑 |
| mapName 兜底 | 若底图管理表中找不到对应记录，`area_name` 字段直接使用 `mapId` 值，前端无需额外处理 |

---

## 八、注意事项

1. **TDengine 空值处理**：TDengine 返回的 NULL 在 Java 中可能被序列化为字符串 `"null"`，本次所有读取 `type`/`map_id` 的地方均做了 `!"null".equals(...)` 的防御性处理；
2. **批量查询性能**：`buildMapIdToNameMap` 使用 `IN` 子句批量查询底图，避免循环单条查询；
3. **软删除兼容性**：`findByIds` 不走 JPA 的 `status` 过滤，确保即使底图被禁用，历史轨迹中的楼层名称仍可解析；
4. **数据依赖**：本次功能依赖 `external_coordinate_data` 表已写入 `type` 和 `map_id` 字段，需确认数据推送端已支持该字段。
